# Performance, load and stress results

Everything below was measured on 2026-11-10 by the scripts named in each section. These are single-machine results and are **not** a capacity claim for any other environment.

**Machine:** Apple M4 Pro (12 logical CPUs), 24 GiB RAM, Docker Desktop (Linux arm64 VM). The load generator (k6 in Docker) ran on the same machine as the system under test, so results include that contention.
**Stack:** PostgreSQL 18 + RabbitMQ 4 + MinIO, API+worker in one container (`QUEUE_CONCURRENCY=2`), processor with 2 OCR slots. Rate limits were raised for the runs (`scripts/run-load.sh` does this and restores them).
**Data:** the API account held about 450 small documents (mostly tiny synthetic invoices), so read paths are warm and cheap. A larger or colder dataset will be slower.

## HTTP load, spike and stress (`./scripts/run-load.sh`)

Each virtual user repeats a journey: list documents → search → stats → open the latest result (4 requests).

| Suite | Shape | Requests | Throughput | p95 latency | Max | Errors | Verdict |
|---|---|---|---|---|---|---|---|
| `load.js` | 20 VUs for 60 s (+ ramp) | 11,013 | 122 req/s | list 29 ms · search 38 ms · result 10 ms | 67 ms | 0.00 % | all thresholds passed (p95 < 500/800/500 ms, errors < 1 %) |
| `spike.js` | 5 → 150 VUs in 5 s, hold 30 s, back to 5 | 49,589 | 582 req/s | 221 ms (all routes) | 418 ms | 0.00 % | passed; latency returned to normal afterwards |
| `stress.js` | steps 25 → 50 → 100 → 200 VUs (30 s each) | 115,461 | 824 req/s | 155 ms | 338 ms | 0.00 % | passed (p99 272 ms < 5 s); **no breaking point was reached at 200 VUs** on this machine |
| `upload.js` | constant 5 uploads/s for 40 s (200 uploads) | 204 | 5 req/s | accept: 21 ms | 34 ms | 0.00 % | the worker kept pace: backlog was empty 1 s after the last upload |
| `ratelimit.js` | 40 login attempts in a burst | 40 | n/a | n/a | n/a | n/a | requests beyond the limit returned `429 RATE_LIMITED` with the standard envelope |

What this shows: the API is not the bottleneck for read traffic at these levels, uploads are accepted quickly, and the pipeline keeps up with 5 tiny documents per second. What it does **not** show: behaviour with large files, cold caches, many gigabytes of data, or a remote database. The stress run stopped at 200 VUs because the machine, not the service, was becoming the limit; run it with larger steps on your own hardware.

Reproduce: `./scripts/run-load.sh` (all suites) or `./scripts/run-load.sh stress`.

## Processor throughput and memory (`./tests/perf/ocr-bench.sh`)

In-process, one file at a time, Tesseract 5.5, 200 DPI rendering.

| Case | File | Pages / rows | OCR pages | Time | Throughput | Peak RSS (growth during the case) |
|---|---|---|---|---|---|---|
| Digital PDF, 1,000 pages | 355 KB | 1,000 | 0 | 0.1 s | ~19,000 pages/s | 111 MB (+2) |
| Scanned PDF, 20 pages (OCR) | 5.9 MB | 20 | 20 | 3.4 s | 5.9 pages/s | 143 MB (+12) |
| Scanned PDF, 100 pages (OCR) | 5.9 MB | 100 | 100 | 17.1 s | 5.8 pages/s | 144 MB (+0) |
| Multi-frame TIFF | 5.6 MB | 2 | 2 | 0.2 s | 9.0 frames/s | 146 MB (+1) |
| CSV, 150,000 rows | 4.2 MB | 150,001 | 0 | 1.4 s | ~107,000 rows/s | 624 MB (+467) |

Findings:

- **Bounded memory for PDFs.** One page image is rendered at a time; peak memory stayed flat from 20 to 100 OCR pages. The test suite also processes a 1,000-page digital PDF well inside its 60 s assertion.
- **OCR time scales linearly** at roughly 6 pages/s per processor slot. A 1,000-page *scanned* PDF would therefore take about 3 minutes with one slot (extrapolated from the 100-page measurement; not run as a single file). The default 900 s processing timeout covers roughly 5,000 scanned pages at this speed.
- **Spreadsheets cost memory proportional to rows** (about 3 KB per row, because every row is returned with its cell coordinates). At the default limit of 200,000 rows that is roughly 0.6 to 0.7 GB, which fits the processor's 3 GB container limit. Raising `MAX_SPREADSHEET_ROWS` substantially needs more memory or a streamed response. This is a known limitation.

`./scripts/run-load.sh` on the local Docker stack (Apple laptop, rate limits raised for the run). Every threshold passed; no failed requests.
